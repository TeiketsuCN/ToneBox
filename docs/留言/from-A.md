```rust
    pub tags: &'a Tags,            // 已有，见 tags.rs

```

**要求：**

1. **只返回参数**，不调 ffmpeg。调用方（我）会把它拼到 `args_for` 后面。
2. **标签**：`-metadata title=…` / `artist=` / `album=` / `track=` / `date=`。
   **空串和 None 不产出**——`-metadata title=` 会把标签写成空值，比不写更糟。
3. **封面**：这是难点，三种容器做法不同，**必须实测**。
   常见做法是 `-i cover.jpg -map 0:a -map 1:v -c:v copy -disposition:v attached_pic`，
   但 `-map` 顺序、`-disposition` 的可用性在 ffmpeg 9 里可能变了。
   如果 `-disposition` 不支持，就退到 `-c:v copy` 让它自己判 attached_pic。
4. **单测**：至少两条——空标签不产出参数；有封面时参数里包含什么。

**验收**：拿一段真 MP3（`D:\Media\Music\cloudmusic\Dj\` 下面有一堆带标签带封面的）

### 下一个任务：`analyze` 的时间上限

**背景**：现在接进 GUI 了，用户选中文件就自动分析。
按你测的 60 个文件 59 秒算，单个 20~35 秒的文件约 1 秒——可接受。
但如果用户拖进来一个 **1 小时的播客 / 一场音乐会录音**，`analyze` 要跑多久？

**要做的事：**

1. **先量，别先改**
   找一个长文件（可以用 ffmpeg 把 `samples/lossless/pop48k_ref.flac` 循环拼成 30 分钟），
   测出当前耗时，写在报告里。**先有数据再决定要不要改。**

2. **如果超过 3 秒，加限时采样**
   频谱特征只跟编码器有关，不需要全曲。
   建议：解码时 `-t` 限制到前 N 秒（比如 90 秒），或者从多个位置各取 20 秒拼接。
   注意：**不要只取开头**——有些歌前奏是纯人声/静音，采样会偏。

3. **顺便确认内存**
   你现在是整段读进内存还是流式处理？1 小时 44.1kHz 立体声 f32 约 1.2 GB，
   如果是整段读入会炸。流式就没问题，但要在报告里写清楚。

**验收**：给一个 30 分钟文件的耗时数字，以及改造前后的对比（如果改了）。
